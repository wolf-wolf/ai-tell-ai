# 冲突消解（Conflict Resolution）

> [!tip] 核心本质
> [[knowledge-fusion|知识融合]] 把多源异构事实写入同一知识库时，同一实体同一属性出现互斥取值是常态；冲突消解要回答的不是简单「选可信度高的来源」，而是在**没有 ground truth** 时，如何估计各候选值为真的后验，并把结果以**置信度、来源与方法**写回，供 [[rag|RAG]] 与人工审核使用。若静默选一个值，会引入隐性错误；若全部保留不加标注，下游会拿到矛盾答案；若一律拒绝写入，库永远不完整——消解是在三者之间找可操作的平衡。

## 生命周期与演进

**当前定位**：知识图谱融合、企业多文档库合并、多版本 API 文档入库的子问题；工程上常与实体对齐并列，位于融合 pipeline 的「写入前」或「定期批处理」阶段。

**预期寿命**：长期。多源数据不会消失；Truth Discovery、复制检测、人机审核门在工业界有成熟实践，但**领域偏见**与**来源不独立**使全自动消解永远需要置信度出口。

**近期演进**：Truth Discovery 与复制关系建模（LTM 等）结合；[[embedding]] / KG 嵌入用于语义一致性检验；低置信度 `needs_review` + LLM 辅助 diff 审核；流式场景下的增量 Truth Discovery（DART）。

**终极威胁**：单一权威源 + 强实时同步使冲突罕见时，消解层变薄；端到端「模型自己融合」可能跳过显式消解决策记录，但在合规与可追溯场景仍需要带来源的写回契约。

## 为什么需要冲突消解

多个来源描述同一实体时，属性值矛盾是常态：Wikipedia 与 Wikidata 对出生年份不同；两份行业报告对营收数字不同；新旧文档对同一 API 参数说明不同。

没有消解机制时只有三条坏路：静默选一个（隐性错误）、同时保留所有值不给元数据（用户看到矛盾）、拒绝写入（库不完整）。实际目标是在**可推断、可审计**的前提下选出或标注「当前最佳」取值。

### 核心困难：没有 ground truth

「查真相」在冲突存在时往往不可行——真相若已知，就不存在冲突。工程问题是：用**间接证据**推断哪个值更可能正确。证据主要来自两方面：来源的历史可靠性，以及候选值被多少**独立**来源支持——对应可信度打分与投票 / Truth Discovery 两条主线。

## 消解方法

### 基于可信度打分

给每个来源一个可信度分数，冲突时优先采用高分来源的值。

- **静态权威度**：人工预设（如百科 > 随机博客）。维护成本低，无法表达领域差异（医学场景 PubMed 可能优于通用百科）。
- **动态声誉分**：用带标注的子集测各来源错误率。需要 ground truth 子集，新来源冷启动难。
- **引用频次**：类似 PageRank；易被**抄袭链**污染——多源抄同一错误时，引用越多反而强化错误。

根本局限：可信度是**来源级**指标，可信来源仍可能在某个事实上出错。

### 投票机制

多个来源独立给出答案，少数服从多数。

- **简单投票**：计票过半获胜。前提：来源相互独立；若多源抄同一库，只是在数副本。
- **加权投票**：票数 × 来源权重。权重定义又回到可信度问题。
- **复制检测 + 投票**：识别拷贝源，同一复制链合并为一票后再投。是修复独立性假设失效的直接手段，也是 Truth Discovery 进阶方向的核心之一。

### Truth Discovery（真相发现）

迭代更新两个互相依赖的量，直至收敛（可视为 EM 式推断）：

- 来源可信度 ← 其支持事实的「正确率」
- 事实正确性 ← 支持它的来源可信度

| 算法 | 核心改进 | 适用场景 |
| --- | --- | --- |
| TruthFinder (Yin 2008) | 最早的迭代可信度传播 | 来源近似独立 |
| Sums / Accu / Pool | 不同传播公式变体 | 大规模 KG，精度要求适中 |
| LTM (Latent Truth Model) | 显式建模复制关系 | 来源间大量抄袭 |
| DART (Li et al.) | 流式增量更新 | 实时数据流 |
| 概率图模型变体 | EM 推断隐变量 | 有理论需求、算力充足 |

核心假设：**来源倾向于说真话**。若领域存在系统性偏见（如低估副作用），算法会自信地收敛到错误共识——监管场景必须保留人工门。

### 基于时间戳

冲突时优先较新来源，但须区分：

- **source_publish_time**：文章何时发布
- **fact_valid_time**：事实何时成立

发布时间新 ≠ 事实新（2024 年文章可引用 1990 年数据）。

| 事实类型 | 时间戳策略 |
| --- | --- |
| 会演变的事实（CEO、人口、软件版本） | 常适用「取新」 |
| 历史事实（战役日期、出生年） | 不宜因新来源随口改写 |

系统应区分 **evolving fact** 与 **historical fact**，避免一律覆盖。

### 语义一致性检验

不只看冲突属性本身，还看与库内其他事实是否逻辑相容。

例：已知「A 公司 2010 年成立」，新来源称「首款产品 2008 年发布」——即使来源权威，也应拒绝或降置信写入。

| 手段 | 特点 |
| --- | --- |
| 规则约束 | 可控，需人工维护规则，长尾难覆盖 |
| KG 嵌入打分（TransE、RotatE 等） | 见 [[embedding]]；低分提示与图结构不符，未必等于逻辑矛盾 |
| LLM 一致性判断 | 灵活，可抓自然语言隐性矛盾，不能作唯一校验 |

### 人工审核

对关键事实或低置信自动结果交人工判定。自动消解输出置信度，低于阈值打 `needs_review`；界面并排展示冲突值、来源与上下文；人工选择写回，并更新来源历史准确率，形成闭环。

## 实践与应用

**场景：两份行业报告对同一公司 2023 年营收不一致**

```
来源 A（权威媒体，2024-03）：营收 120 亿
来源 B（分析机构，2024-06）：营收 115 亿

Step 1：冲突检测 → 同一实体、同一属性、两值
Step 2：Truth Discovery → A 历史准确率 0.85，B 0.72 → A 置信 0.63，B 0.37
Step 3：语义一致性 → 两值均在合理区间，无逻辑矛盾
Step 4：0.63 < 阈值 0.8 → needs_review
Step 5：人工 → A 引用官方财报，B 为估算 → 选 A

写回：营收 120亿, confidence: 0.9, source: A, reviewed_by: human
```

若跳过 Step 4 自动选 A，结果可能对，但缺少审核记录与来源追溯，后续无法解释「为何是 120 亿」。

生产写回契约建议：保留**消解方法**、**置信度**、**支持来源**；高价值域低置信度不得自动入库；原始冲突候选可归档以便新来源到达时**重新消解**。

## 坑与误区

- **Truth Discovery 等于 ground truth**：统计意义上的「多数可信源支持」；全行业系统性错误时，算法会高置信犯错。医疗、法律、金融等须人工校验。
- **选一个值就结束**：应写回置信度与来源，并保留冲突历史供再消解；下游 [[rag]] 可依置信度决定是否引用。
- **新的永远更对**：仅适用于演变型事实；历史事实不能因新报道覆盖。
- **来源级可信等于事实级正确**：须结合投票、复制检测、一致性检验与人工门。

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 来源不独立 | 抄袭膨胀票数 | 复制检测，同源合并一票 |
| 系统性偏见 | 高置信错误共识 | 监管域人工门 + 领域规则 |
| 时效混淆 | 历史事实被覆盖 | 区分 evolving / historical |
| 不可追溯 | 无法解释取值来源 | 方法 + 来源 + 置信度写回 |

## 工具与实现

冲突消解无统一框架，实现分散在算法库与审核 UI：

**Truth Discovery**

- [CrowdKit](https://github.com/Toloka/crowd-kit)（Toloka）：TruthFinder、Dawid-Skene、GLAD、MACE 等，sklearn 风格 API，偏众包质量控制但 TD 是核心能力之一。
- 论文配套仓库（truth-discovery、CATD 等）多已停更，适合算法学习而非生产默认。

**嵌入一致性检验**

- [OpenKE](https://github.com/thunlp/OpenKE)：TransE / RotatE 等，为候选三元组相对现有图结构打分。

**人工审核**

- 常集成在知识库 CMS；[Label Studio](https://github.com/HumanSignal/label-studio) 可搭冲突 diff 与多标注者对比界面。
