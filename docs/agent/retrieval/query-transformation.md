# 查询转换（Query Transformation）

> [!tip] 核心本质
> 用户的口语化提问和知识库的书面语文档之间存在「语义鸿沟」——同一件事的表达差距可以让向量距离非常远。查询转换在检索发生**之前**，把含糊的用户意图变换成向量/BM25 更容易命中的形态。它解决的不是「模型不够聪明」，而是「输入对齐」问题：垃圾进，垃圾出。

## 生命周期与演进

**当前定位**：高级 RAG 流水线的标配前置阶段；简单场景（直接明确的问题）跳过改写不影响质量，检索失败时才是必要手段。

**预期寿命**：中期。手写 Prompt 拼接式的改写框架会逐渐被 DSPy 类编译器和轻量 SLM 替代；但「意图对齐」这个问题本身长期存在。

**近期演进**：SLM 化（百兆小模型专职做微秒级改写）；CRAG / LangGraph 把改写降级为 Fallback 节点而非必经步骤；bge-m3 等模型同时输出 dense + sparse 向量，降低了语义鸿沟对召回的伤害。

**终极威胁**：超长上下文（10M+ token）中小知识库直接全量入窗口绕过检索；端到端检索模型自带改写 head。但大型私有知识库中显式改写仍有工程价值。

---

## 为什么需要查询转换

没有查询转换时系统的典型失败模式：

| 失败模式 | 例子 | 根因 |
| --- | --- | --- |
| **代词指代** | 多轮对话中问「那它呢？」 | 检索器拿「那它呢」去查，语义无效 |
| **词汇不匹配** | 用户说「输出不稳定」，文档写「Temperature 参数漂移」 | 向量距离大，漏召 |
| **多跳问题截断** | 「A 和 B 的价格差」 | 单次检索偏向一个实体，另一个漏掉 |
| **疑问句 vs 陈述句** | 「怎么配置 X？」vs 文档「X 的配置方法是...」 | 句型不同导致向量偏移 |
| **跨语言鸿沟** | 中文问题检英文库 | 跨语言 embedding 质量因模型而异 |

## 五类核心手段

### 1. 查询改写（Query Rewriting）

结合多轮对话历史，把指代不明或语境缺失的短句补全为**独立完整的陈述句**，消除代词指代和上下文依赖。

```
历史：用户问了「什么是 HNSW」
当前：「那它的时间复杂度是多少？」

改写后：「HNSW（Hierarchical Navigable Small World）的查询时间复杂度是多少？」
```

实现方式：一次 LLM 调用，Prompt 包含近几轮对话历史，要求输出独立完整的查询。

---

### 2. HyDE（Hypothetical Document Embeddings）

**问题**：疑问句（「如何配置 X？」）和陈述句（「X 的配置步骤是...」）在向量空间差距很大。

**HyDE 的反直觉做法**：不直接检索原问题，而是先让 LLM 生成一段「假设答案」（内容可能是错的），再用假设答案的 embedding 去检索真实文档。

```
原问题：「HNSW 的 ef_search 参数怎么调？」
                    ↓ LLM 生成假设答案
假设答案：「ef_search 控制搜索时的候选列表大小，值越大召回越高但延迟增加，
           一般从 50 开始调，目标召回率 95% 时通常设 100–200...」
                    ↓ 用假设答案的 embedding 检索
真实文档：「ef_search 参数说明...」（向量距离更近，命中率更高）
```

**为什么有效**：假设答案的**句型和术语分布**与真实文档类似，即使事实错误，向量表示也更接近目标文档。本质是用幻觉特性解决对齐问题。

**适用场景**：专业领域文档（医疗、法律、技术手册），用户口语表达和文档书面语差距大时效果最显著。

---

### 3. 多查询扩展（Multi-Query Expansion）

让 LLM 从**多个角度**改写同一个问题，生成 N 个语义相近但措辞不同的查询，分别检索后用 [[rrf]] 融合结果。

```
原问题：「向量数据库怎么选？」

扩展为：
  - 「主流向量数据库有哪些，各自的优缺点是什么？」
  - 「Milvus、Qdrant、Weaviate 的性能对比」
  - 「生产环境中向量数据库的选型标准」
  - 「embedding 存储和检索的开源方案」

→ 四路并发检索 → RRF 融合
```

**效果**：单个改写可能方向错，多路并行覆盖更广，RRF 融合后噪声被平滑。

**代价**：N 次检索 + N-1 次额外 LLM 调用（或一次批量调用），延迟随 N 线性增长。N=3 是常见折中。

---

### 4. 子查询分解（Sub-query Decomposition）

针对**多跳（multi-hop）**或**聚合型**问题，拆分为若干独立子查询，分别检索后再合并答案。

```
原问题：「A 产品和 B 产品的价格差是多少，哪个更适合中小企业？」

拆分为：
  - 子查询 1：「A 产品的定价方案」
  - 子查询 2：「B 产品的定价方案」
  - 子查询 3：「中小企业选型的评估标准」

→ 三路并发检索 → 聚合上下文 → LLM 综合回答
```

与多查询扩展的区别：多查询扩展是「同一问题的不同问法」（并行且等价），子查询分解是「一个复杂问题的不同部分」（并行但互补）。

---

### 5. Step-back Prompting（抽象化改写）

先把具体问题「退一步」提升为更抽象的通用问题，再用抽象问题检索背景知识，辅助回答具体问题。

```
具体问题：「bge-reranker-v2-m3 在 A10 GPU 上处理 50 个候选的延迟是多少？」

Step-back：「Cross-Encoder Reranker 的性能特征和延迟影响因素」

→ 先检索抽象问题（获取背景）→ 再检索具体问题（获取细节）→ 组合上下文
```

**适用场景**：高度具体的查询在库中可能没有精确匹配，但相关背景知识有助于 LLM 推断答案。

---

### 6. 语言归一（Language Normalization）

多语言知识库中，将非主语言查询翻译为主语言后再检索，避免跨语言 embedding 质量参差不齐。

```
用户：（日语提问） → 翻译为英语/中文 → 检索英文/中文库 → 生成回答
```

**注意**：`bge-m3` 等多语言模型在主流语言对上跨语言检索质量已较好，语言归一的必要性视模型而定。

---

## 决策：什么时候引入改写

改写每次增加至少一次 LLM 调用（约 100–500ms），不应默认开启。

```
检索失败分析
│
├── 召回为空 / 相关文档排名靠后？
│     ├── 是，且原因是「词汇不匹配」      → 加 HyDE 或查询改写
│     ├── 是，且原因是「问题多跳/聚合」    → 加子查询分解
│     └── 是，且原因是「表述角度单一」     → 加多查询扩展
│
├── 召回正确但答案不完整？
│     └── 问题太具体，缺背景知识            → 加 Step-back
│
└── 召回已经够好？
      └── 不需要改写，跳过
```

**现代架构（CRAG 模式）**：先用原始 Query 检索并打分，得分低时才触发改写，避免无谓的延迟惩罚。

```python
def modern_rag_workflow(user_query, history):
    docs, score = retrieve_and_grade(user_query)

    if score < THRESHOLD:
        # 得分不足才改写，用轻量 SLM 降低延迟
        rewritten = slm_rewriter.rewrite(user_query, history)
        docs, _ = retrieve_and_grade(rewritten)

    return llm.generate_answer(docs, user_query)
```

## 各手段对比

| 手段 | 解决的问题 | 额外延迟 | 适用场景 |
| --- | --- | --- | --- |
| 查询改写 | 代词指代、上下文缺失 | 1× LLM 调用 | 多轮对话场景 |
| HyDE | 疑问句 vs 陈述句向量偏移 | 1× LLM 调用 | 专业领域，口语 vs 书面语差距大 |
| 多查询扩展 | 单一角度覆盖不全 | N× LLM 调用 + N× 检索 | 通用场景，召回率优先 |
| 子查询分解 | 多跳/聚合问题截断 | N× LLM 调用 + N× 检索 | 多实体比较、聚合分析 |
| Step-back | 具体问题缺少背景知识 | 1× LLM 调用 + 1× 额外检索 | 高度具体查询 |
| 语言归一 | 跨语言向量质量不均 | 1× 翻译调用 | 多语言混合库 |

## 工具与框架

| 框架 | 特点 | 适用 |
| --- | --- | --- |
| [LangGraph](https://github.com/langchain-ai/langgraph) | 将改写降级为状态图中的 Fallback 节点（CRAG 范例） | 生产级，按需触发 |
| [DSPy](https://github.com/stanfordnlp/dspy) | 自动优化改写 Prompt，无需手写，按答案准确率指标编译 | 自动化优化 |
| [Qwen2.5-1.5B](https://github.com/QwenLM/Qwen2.5) / [Phi-3-Mini](https://github.com/microsoft/Phi-3CookBook) | 轻量 SLM，微调后专职改写，百毫秒内完成 | 延迟敏感场景 |
| [Self-RAG](https://github.com/AkariAsai/self-rag) | 模型通过输出 `[Retrieve]` token 自决定是否检索，内化改写意图 | 研究原型 |
