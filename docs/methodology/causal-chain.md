# 因果链

> [!tip] 核心本质
> 因果链是把「为什么」问到底的结构化工具：将一个现象或结论拆解为有序的原因序列，每个节点都能回答「它为什么发生」，并指向可干预的位置。没有它，AI 系统的设计与调试就会停留在「现象描述」层——你能看到 Agent 输出错了，却不知道是 Prompt 结构、工具描述、知识缺口还是 Embedding 语义偏差导致的；你能识别系统有问题，却说不清改哪一层能修复，也说不清改了之后会不会引入新问题。

## 生命周期与演进

**当前定位**：AI 系统设计、调试与文档写作的核心思维工具。不是一个技术组件，而是贯穿所有层次的分析框架——用于判断「这个组件为什么在这里」「这个现象的根源在哪」。

**预期寿命**：Permanent——因果推理是科学方法的底层认识论工具，不随 LLM 架构版本或 Agent 框架迭代而过时。只要还有「为什么出错」和「改哪里能修复」这两类问题，因果链就有效。

**近期演进**：随 LLM 能力增强，「因果链显式化」从人工完成（分析报告、设计文档）扩展到 LLM 辅助生成——Chain of Thought 让模型在上下文里写出推理步骤，本质是把内隐的因果链变成可检查的文本序列。

**终极威胁**：无直接替代威胁。因果链会被吸收进 Planning、Reflection、ReAct 等更高阶的 Agent 模式，成为隐式基础设施——但思维工具本身不会消亡，只会以不同形式被制度化。

## 基础概念

### 因果 vs 相关

因果链的起点是厘清「相关」和「因果」的边界：

```
相关（Correlation）：A 和 B 同时出现，或同向变化

因果（Causation）：A 发生 → B 发生
                   且移除 A 后，B 不发生（反事实成立）
```

这个区分在 AI 系统里尤为重要，因为相关性陷阱无处不在：

- **「RAG 召回率高，回答质量更好」**——相关，不是因果。提升召回率不必然提升质量，缺失的因果链是：召回 → 相关性精排 → 上下文注入 → 模型能否利用 → 最终质量。每个节点都可能断链。
- **「换了新模型，效果变好了」**——如果不追问因果链（参数量、RLHF 数据质量、context window 变大，还是恰好 system prompt 也改了？），就无法复现或维持这个提升，也无法判断下次升级时哪个因素才是关键。

停留在相关性层面做优化，是猜测，不是工程。

### 因果链的三个层次

分析一个 AI 系统问题，因果链天然分三层：

**描述层（What）**：事件序列的字面记录
```
用户提问 → RAG 召回 → LLM 生成 → 答案错误
```

**机制层（Why/How）**：每个节点背后的运作原因
```
答案错误
  ← LLM 生成阶段产生幻觉
    ← 上下文中缺少相关证据
      ← RAG 召回未命中正确文档
        ← 查询向量与文档向量语义距离过大
          ← 用户使用口语提问，文档使用专业术语体系
```

**干预层（Where to change）**：哪个节点可以介入，断链或修链
```
可介入点：Query Transformation
→ 将口语查询改写为与文档匹配的术语
→ 断开「语义距离过大」这个链节
→ 修复整条因果链，不需要改动其他节点
```

只有到机制层，才能确定干预点。停在描述层，所有优化都是盲目的。

## 两个推演方向

因果链可以正向或逆向展开，对应设计和调试两个场景。

### 正向推演：从原因到结果（设计场景）

正向推演用于系统设计——给定已知条件，推导「如果我们做 X，会发生什么」：

```
决策：引入 Query Transformation

正向推演：
用户口语查询
→ 改写为术语查询
→ 向量相似度命中率提升
→ 召回文档相关性提升
→ 上下文质量提升
→ 模型幻觉减少
→ 回答准确率提升

副作用链：
改写 → 消耗额外 LLM token（成本增加）
改写 → 增加响应延迟（需要评估是否可接受）
```

正向推演在设计阶段让你提前看到副作用，而不是上线后才发现。

### 逆向推演：从结果到原因（调试场景）

逆向推演用于调试——给定一个错误现象，追溯「这个结果是什么原因造成的」：

```
现象：Agent 反复调用了错误的工具

逆向推演：
调用错误工具
← Tool selection 判断错误
  ← 模型对工具用途的理解有歧义
    ← 工具 A 和工具 B 的 description 描述场景重叠
      ← 工具设计时未明确区分边界场景
        ← 工具命名和描述语言不精确

干预点：修改工具 description，添加「适用/不适用」边界示例
```

如果只看「调用了错误的工具」就直接改 system prompt 的全局指令，不追因果，很可能改了无效位置，或解决了一个问题又引入另一个工具的混淆。

## 反事实检验：验证因果链的方法

判断因果链是否正确，最可靠的方法是**反事实测试**：移除某个节点，结果还会发生吗？

```
声明："Query Transformation 提升了 RAG 的召回准确率"

反事实检验：
① 只做 Query Transformation，不改 Embedding 模型 → 准确率变化幅度？
② 只换 Embedding 模型，不做 Query Transformation → 准确率变化幅度？
③ 两者都做 → 幅度是 ① + ② 的线性叠加，还是有交互效应？

结论：
→ 若 ① 效果显著，② 效果微弱，因果链中 Query Transformation 是主因
→ 若 ② 效果显著，因果链需要修正：Embedding 质量是更上游的断链点
```

这种检验在系统工程里叫消融实验（Ablation Study）。在日常设计决策中，把反事实问题内化为习惯：**「如果去掉这个组件，系统会在哪里出问题？」**——这个问题既能验证组件的必要性，也能暴露假设的因果链是否成立。

## 在文档写作中的应用

写作规则要求「因果密度，不是篇幅堆砌」，核心是将隐性的因果链显式化。

| 写法类型 | 示例 | 问题 |
|---------|------|------|
| 描述式（无因果） | 「RAG 能提升回答质量」 | 为什么？在什么条件下？ |
| 相关式（伪因果） | 「用了 RAG 的系统效果更好」 | 混淆相关与因果，无法复现 |
| 因果式 | 「RAG 通过将外部文档注入上下文，弥补模型的知识截止局限，从而在知识密集型任务上减少幻觉」 | 完整——说清了机制和适用边界 |

判断一段说明是否有足够因果密度，可以用「所以呢？」测试：

> 「RAG 召回了相关文档。」——所以呢？  
> 「所以上下文里有了依据。」——所以呢？  
> 「所以模型不需要依赖参数里可能错误的记忆来回答。」——到这里，因果链才封闭。

## 与 Agent 推理模式的关系

因果链是多个 Agent 推理模式的底层支撑，各模式对应因果链的不同遍历方向：

| 模式 | 因果方向 | 核心操作 |
|------|---------|---------|
| [[planning]] | 逆向：从目标反推前置条件 | 拆解「要实现 X，需要先有什么」 |
| [[chain-of-thought]] | 正向：从已知条件逐步推导 | 让模型在 context 里写出推理链节 |
| [[reflection]] | 逆向追溯：从错误输出找出问题节点 | 对已生成结果做因果复盘 |
| [[reAct]] | 正向 + 反馈循环 | 行动 → 观察 → 更新因果模型 → 下一步 |

这四个模式不是替代因果链，而是把因果链的不同遍历策略制度化为可操作的 Agent 行为框架。
