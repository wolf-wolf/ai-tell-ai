# BM25（Best Matching 25）

> [!tip] 核心本质
> **BM25** 是关键词检索的**相关度打分公式**：给定查询词与文档，在倒排索引已筛出候选文档后，用 TF（词频）、IDF（逆文档频率）和文档长度归一化算出一个分数，按分排序返回 Top-K。它不是搜索引擎本身——**倒排索引负责「找谁含有这些词」，BM25 负责「谁更相关」**。若没有 BM25 这类排序，关键词检索只能返回「含词即命中、长短不分」的粗糙列表；RAG 混合召回里 BM25 路也因此仍是工业标配，与 [[ann|向量检索]] 互补而非被替代。

## 生命周期与演进

**当前定位**：BM25（Okapi 变体，Robertson & Walker 1994）仍是 Elasticsearch、Lucene、OpenSearch 的**默认文本相关性模型**；RAG 生产系统几乎一律采用 **BM25 + Dense 混合召回**，再经 [[rrf]] 融合。嵌入式场景由 [[fts5]]、Tantivy 等提供同等排序能力。

**预期寿命**：长期稳定。算法来自 1990 年代 IR 研究，经 TREC、BEIR 等 benchmark 反复验证；新模型（SPLADE、learned sparse）在部分榜单上超越 BM25，但 BM25 仍是**无训练、可解释、零冷启动**的 baseline。

**近期演进**：向量库原生 BM25（Milvus 2.5+、Qdrant sparse）；**bge-m3** 等模型同时输出 dense + learned sparse，稀疏路在语义上接近 BM25 角色但需模型推理；ColBERT 等 late interaction 介于 BM25 与单向量之间。

**终极威胁**：端到端神经检索在特定域完全替代手工公式；超长上下文下「少检索」削弱关键词路权重。但**精确 token 匹配**（错误码、API 路径、法规编号）在可预见期内仍需要词法级检索，BM25 或其稀疏后继长期存在。

## 问题背景：关键词检索的两步

一次关键词检索分两步，BM25 只参与第二步：

```mermaid
flowchart LR
  Q[查询分词] --> INV[倒排索引查 posting list]
  INV --> CAND[候选文档集合]
  CAND --> BM25[BM25 打分排序]
  BM25 --> TOP[Top-K 结果]
```

**倒排索引**把「词 → 文档列表」预建好（见下文），查询 `"deploy error"` 时取各词 posting list 的交集/并集，**不扫全库**——复杂度从 O(N) 降到 O(命中 posting 数)。

**BM25** 在候选集上为每个 (query, document) 对算分并排序。没有它，常见退化是：超长文档因词频堆叠霸榜，或短而精准的文档被淹没。

## 从 TF-IDF 到 BM25

### TF-IDF 的局限

经典 **TF-IDF**：

```
score(q, d) = Σ tf(t, d) × idf(t)
idf(t) = log(N / df(t))
```

- **TF 线性增长**：词出现 100 次比 10 次分高 10 倍——长文档天然占优。
- **无长度归一化**：一页纸和一句话不可比。
- **无词频饱和**：第 11 次出现与第 1 次同等加权。

### BM25 的三项改进

BM25Okapi 核心形式（对查询中每个 term *t* 求和）：

```
score(q, d) = Σ  IDF(t) ×  ( TF(t,d) × (k₁ + 1) ) / ( TF(t,d) + k₁ × (1 - b + b × |d|/avgdl) )
```

先把这条式子“翻译成人话”：

- `q`：你的查询（query），比如 `agent memory`
- `d`：某一篇候选文档（document）
- `t`：查询里的某个词（term），比如 `agent`
- `score(q,d)`：这篇文档对这次查询的总分（越高越相关）
- `Σ`：求和符号，意思是“把查询里每个词的分数都加起来”
- `×`：乘法，意思是“两个因素共同起作用”（某一项为 0，整体贡献就接近 0）
- `/`：除法，这里主要用于“归一化/抑制过大值”（防止词频无限放大）
- `|d|`：文档长度（词数）
- `avgdl`：整个语料库文档平均长度

术语速查（最常问的三个）：

- **TF（Term Frequency）**：某个词在**当前文档 d** 里出现了几次。  
  例：`agent` 在文档 A 出现 3 次，则 `TF(agent, A)=3`。
- **IDF（Inverse Document Frequency）**：某个词在**整个语料库**里有多稀有。  
  很常见的词（很多文档都有）IDF 小；稀有词 IDF 大。
- **avgdl（average document length）**：语料库里文档的平均长度（通常按词数）。  
  例：三篇文档长度分别为 100、200、300，则 `avgdl=(100+200+300)/3=200`。

一句话记忆：**TF 看“这篇里出现几次”，IDF 看“全库里稀不稀有”，avgdl 是“全库平均篇幅”（用于长度纠偏）。**

再看公式结构，可以拆成：

`总分 = Σ( 词重要性 × 词频贡献 )`

其中：

- `词重要性 = IDF(t)`  
- `词频贡献 = ( TF × (k₁+1) ) / ( TF + k₁ × (1 - b + b × |d|/avgdl) )`

按步骤理解（和上式一一对应）：

1. **先拆词**：把查询 `q` 拆成多个词 `t`（例如 `agent`、`memory`），每个词单独计算。
2. **算单词贡献**：对每个 `t`，先算 `IDF(t)`（词重要性），再算右侧分式（词频贡献，含饱和和长度修正），两者相乘得到该词贡献。
3. **做长度纠偏**：右侧分式里的 `|d|/avgdl` 会校正文档长短差异，避免长文档因为“词多”天然占优。
4. **最后求和**：把所有词贡献用 `Σ` 相加，得到 `score(q,d)`，分越高排名越靠前。

可以把它类比成“课程总评”：`IDF` 像课程权重，右侧分式像单科成绩，`Σ` 像总分汇总。  
> 乘法表示“重要性和匹配程度要同时成立”；加法表示“多词查询的每个词都贡献总分”。

**什么是“长度纠偏”**（也叫长度归一化）：

- 含义：在打分时，把文档“天生长或短”带来的优势校正掉，尽量只比较相关性。
- 为什么要做：长文档词更多，更容易“碰巧命中”查询词；不纠偏会让长文档虚高。
- 在 BM25 里怎么做：用 `|d|/avgdl` 比较当前文档与平均长度，再由参数 `b` 控制纠偏强度。  
  - `b=0`：不做长度纠偏；  
  - `b=1`：完全按长度比例纠偏；  
  - 常用 `b≈0.75`：适中纠偏。
- 直觉例子：两篇文档都命中关键词 3 次，A 长度 100 词，B 长度 2000 词。  
  纠偏后会认为 A 的 3 次更“密集”，B 会被适度降权。

一句话记忆：**长度纠偏不是“惩罚长文档”，而是防止“因为长所以占便宜”。**

| 组件 | 含义 | 作用 |
| --- | --- | --- |
| **IDF(t)** | 稀有词权重高 | `log((N - df + 0.5) / (df + 0.5) + 1)` 等变体；常见词降权 |
| **TF 饱和项** | 分子 `(k₁+1)×TF`，分母含 TF | 词频增加时分数**趋近上限**，不会无限涨 |
| **长度归一化** | 参数 **b** × 文档长/平均长 | 惩罚过长文档的「凑词」 |

**超参数**（Lucene / ES 默认接近）：

| 参数 | 典型值 | 调大效果 |
| --- | --- | --- |
| **k₁** | 1.2 – 2.0 | 词频饱和更慢，高 TF 文档更占优 |
| **b** | 0.75 | 长度惩罚更强；0 = 不归一化，1 = 完全按长度比例 |

> BM25 是 **Best Matching 25** 的缩写，指 Okapi 系列中第 25 次迭代的调参版本——名字来自 IR 实验编号，不是数学常数。

## 倒排索引：BM25 的运行时依赖

BM25 公式本身无状态；工程上它总是跑在**倒排索引**之上：

```
正排：doc → tokens
  doc1: ["deploy", "error", "kubectl"]
  doc2: ["deploy", "rollback", "script"]

倒排：token → [(doc, tf, positions…)]
  "deploy" → [(doc1, 1), (doc2, 1)]
  "error"  → [(doc1, 1)]
```

Posting list 存 **TF**、可选 **position**（支持短语查询）、**DF**（算 IDF）。索引构建在 ingest 时完成；查询时只读 posting list + 算 BM25。

实现载体（算法相同，规模与运维不同）：

| 实现 | 场景 |
| --- | --- |
| Elasticsearch / OpenSearch | 分布式生产 RAG、日志搜索 |
| Lucene / Tantivy | ES 底层；Rust 嵌入式 |
| [[fts5]] | 单机 SQLite，Agent 会话库 |
| `rank_bm25` | Python 小库、教学/POC |
| Milvus BM25 function | 向量库内混合检索 |

倒排索引与 BM25 的**分工**：索引 = 数据结构；BM25 = 排序函数。FTS5 是「索引 + 查询语法 + 内置 bm25()」的**打包实现**，不是「FTS5 封装 BM25」这么简单——见 [[fts5]]。

## 与向量检索的分工

| 维度 | BM25（稀疏 / 词法） | Dense 向量（[[ann]]） |
| --- | --- | --- |
| 表示 | 离散 token + 倒排 | 连续 embedding |
| 匹配方式 | 词重合（经 IDF 加权） | 语义距离 |
| 擅长 | 错误码、API 名、SKU、法规条款号 | 同义改写、口语 vs 书面语 |
| 弱点 | 「汽车」搜不到只写「车辆」的文档 | 「ORA-01000」可能被语义相近但无关的 chunk 淹没 |
| 索引成本 | 分词 + 倒排，无 GPU | Embedding 模型 + 向量索引 |
| 分数尺度 | BM25 分（无界） | [[cosine-similarity]] 等 Dense 度量 |

混合召回架构、消融与 Rerank 分工见 [[retrieval-pipeline]]；BM25 与向量分**不可直接加权求和**，须用 [[rrf]] 融合排名。

## 实践要点

### 分词与语言

BM25 质量上限由 **tokenizer** 决定：英文按空格+词干（Porter）即可；中文需 jieba、IK Analyzer 等，否则整句成一个大 token，检索退化为 substring。CJK 场景常配合 trigram 或 n-gram 倒排（[[fts5]] 的 trigram 表即此类）。

### 查询侧技巧

- **多词默认 AND**：ES/Lucene 对空格词常作 AND；漏召回时可 OR 扩展（[[query-transformation]]）。
- **短语**：引号 `"session search"` 依赖 position index。
- **字段权重**：标题 BM25 分 × 10、正文 × 1——Lucene 的 `boost`，FTS5 的 `bm25(table, w_title, w_body)`。

### 最小 Python 示例（rank_bm25）

```python
from rank_bm25 import BM25Okapi

corpus = [
    "kubectl apply deploy yaml",
    "fix ORA-01000 max open cursors",
    "rollback script after failed deploy",
]
tokenized = [doc.lower().split() for doc in corpus]
bm25 = BM25Okapi(tokenized)

query = "deploy error".lower().split()
scores = bm25.get_scores(query)
# scores[i] 即 BM25 分；argsort 取 Top-K
```

生产环境应用 ES/Milvus/FTS5，而非内存 `rank_bm25`——上例仅说明**公式输入是 token 列表 + 倒排统计**。
